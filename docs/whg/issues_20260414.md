# WHG API Issues — 2026-04-14

Draft issues for filing on the WHG GitHub repository. Context in `api_investigation.md`.

## Issue 1: `/suggest/entity` ranking does not reflect data richness

**Endpoint:** `GET /suggest/entity`

**Summary:** All candidates return score=100 regardless of historical significance or data coverage, making "take top result" unreliable for place-lookup UX.

**To reproduce:**
```
GET /suggest/entity?prefix=Edinburgh&limit=5&token=...
```

Top result: "Edinburgh of the Seven Seas" (Tristan da Cunha, SH). "Dùn Èideann" (Edinburgh, Scotland, `place:gn:2650225`) is third, tied at score=100 with a US hamlet.

**Observed vs. expected:**

The WHG GUI itself ranks candidates by linked record count — Midlothian appears first for "Edinburgh" because it has 5 linked records in the elastic index. This data exists in the index but is not used to break score ties in the API response.

**Impact:** Any application that takes the top suggest result without user confirmation will silently resolve to the wrong place. Our workaround is to present all candidates to the user for selection, which is the correct UX but adds friction.

**Concrete ask:** Use linked record count (or attestation count) as a tiebreaker when scores are equal, consistent with how the WHG GUI already ranks results. Alternatively, expose a `sort_by=linked_records` parameter.

## Issue 2: `fclasses` filter uses AND semantics instead of ANY

**Endpoint:** `GET /suggest/entity`, `POST /reconcile`

**Summary:** The `fclasses` filter excludes records whose fclasses set is not an exact match for the requested class, rather than returning any record that includes the requested class.

**To reproduce:**
```
GET /suggest/entity?prefix=Timbuktu&fclasses=P&limit=5&token=...
```

Returns a US hamlet (fclasses: `["P"]`) as top result. Tombouctou, Mali (`place:5424806`, fclasses: `["P","S"]`) is excluded, despite being a populated place.

**Expected behavior:** `fclasses=P` should return any record that has `P` among its fclasses — i.e., ANY match, not AND/exact-set match. This is consistent with the LPF documentation note that `["A","P"]` finds "both settlements and municipalities" — which implies OR semantics at the query level.

**Impact:** Historical settlements commonly carry dual classification (`P+S`, `A+P`). A filter for `P` (populated places) silently excludes the majority of historically significant cities in the index. We removed the fclasses filter from our implementation entirely as a workaround.

## Issue 3: `period:` entities are not excluded by spatial or feature-class filters

**Endpoint:** `GET /suggest/entity`

**Summary:** PeriodO period entities (`period:...`) appear in suggest results even when `fclasses` and `countries` filters are specified, because those filters apply only to place-type entities.

**To reproduce:**
```
GET /suggest/entity?prefix=Ur&fclasses=S&countries=IQ&limit=5&token=...
```

Returns `period:` entries (e.g. "Ur III", "Uruk") at score=100 above place results for Ur (Tell al-Muqayyar, Iraq).

**Expected behavior:** A query filtered by `fclasses` and/or `countries` is implicitly a place query. Period entities should not appear in results, or there should be an explicit `entity_type=place` parameter to exclude them.

**Impact:** Clients must filter results client-side on `id.startsWith("place:")` to avoid noise. This is a leaky abstraction — the filter parameters imply place-only results but don't enforce it.

## Issue 4: `/reconcile` returns child namespace IDs; these are incompatible with `/entity` and `/suggest`

**Endpoint:** `POST /reconcile`

**Summary:** The reconcile endpoint returns source-namespace IDs (`place:gn:2449067`, `place:wd:Q9427`) rather than WHG canonical parent IDs (`place:5424806`). These IDs cannot be used with the `/entity/{id}/api` endpoint to retrieve geometry or fclasses, and are a different ID space from `/suggest/entity` results.

**Background:** We initially used reconcile to get candidates, then called `/extend` to retrieve geometry. The extend call returned empty `geometry_wkt` for child IDs. Switching to suggest+entity (N+1 HTTP calls) was the only workaround.

**To reproduce:**
```
POST /reconcile
{"queries": {"q1": {"query": "Timbuktu", "fclasses": ["P"]}}}
```

Returns `place:gn:2449067`. Calling `GET /entity/place:gn:2449067/api` returns sparse properties with no geometry. The canonical parent `place:5424806` (which has full geometry) is only discoverable via suggest.

**Concrete ask:** Either (a) add a `return_canonical=true` option to reconcile that returns WHG parent IDs, or (b) document explicitly that reconcile IDs are child namespace IDs, cannot be used with `/entity`, and are a different ID space from suggest results.
