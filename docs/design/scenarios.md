# EDOPS User Scenarios

Scenarios ground both signature design and UI/UX design in real research questions. A good scenario starts from a **historical paradox** or **research need** — not a task flow. The signature's job is to resolve or deepen the paradox, or to supply structured environmental context that a researcher's own workflow can consume.

Scenarios may or may not involve the sandbox GUI. Some run entirely through the API. Over time, elements developed in the sandbox will migrate into a more polished researcher dashboard where users can configure the API call appropriate to their purpose — potentially through named **API lenses** (pre-configured band/neighborhood/format profiles for common use-case classes).

## User Profiles

### user00 · Karl (instrument designer / PI)
Geographer and spatial humanities researcher building EDOPS. Uses the sandbox both to develop and validate the signature — probing real places to see whether the output tells a true story. Requirements generated by Karl's exploratory use are instrument design requirements, not just GUI preferences. Karl's scenario type: *expose a gap, specify a fix, iterate*.

### user01 · humanities researcher (sandbox GUI)
Historian, archaeologist, classicist, or heritage professional pursuing questions with a spatial/geographic component. Typically non-computational: uses the sandbox interactively, reads signature output in band panels, triggers LLM narrative interpretation. Entry point is a place name or question, not an API call.

### user02 · Federico (computational classicist / API integrator)
PhD in Classical Literature + BSc in Software Engineering. Builds AI- and knowledge-graph–based retrieval systems for ancient-world corpora. Current project: spatial Graph-RAG over water infrastructure texts, with environmental enrichment of place nodes in Neo4j. Uses EDOPS programmatically via the API; the sandbox GUI is a configuration aid, not the primary interface. Primary corpus is pre-Common Era — the temporal gap is a hard constraint for his use case, not an edge case.

## Scenarios

### scenario 00 · Karl / Tombouctou — exposing the basin assignment problem *(instrument design)*

**User**: user00 (Karl)

**Entry need**: *"I need to know whether the signature EDOPS returns for Timbuktu actually captures the environmental conditions that made it viable as a civilizational center — or whether it's returning the signature of a small, locally arid patch of ground that misses the Niger entirely."*

**What happened** (2026-04-11 session):
1. Karl resolved "Tombouctou" via WHG → coordinates 16.8167, −2.9833. Default Level 08 basin was assigned: 588 km². The signature for that basin read as Saharan-margin arid — plausible locally but environmentally incomplete.
2. The neighborhood preview map (newly built) showed the assigned basin (orange) surrounded by much larger basins, the largest nearby being 381,370 km² — the Niger main channel system. The visual made the assignment problem immediately legible: the city sits at the edge of one small basin, adjacent to an enormous one that carries the actual water.
3. The current assignment logic (point containment at Level 08) systematically misassigns floodplain, delta, and river-adjacent sites to their local micro-basin rather than the dominant hydro-context.

**Requirement generated**: neighborhood preview map (now implemented) showing assigned basin, adjacent basins colored by upstream area, and main river lines — so the user can assess whether the default assignment is hydrologically appropriate before requesting a signature.

**Open design question**: what should happen *after* the user sees the preview and recognizes the mismatch? Current behavior: "Get signature" proceeds with the containment assignment. Future behavior: user selects a basin from the preview, or the system applies `find_main_basin()` (max `up_area` within radius) as the default. The rubric for choosing the right neighborhood is the next design problem this scenario exposes.

**Design implications**:
- Neighborhood assignment must be visible and overridable, not a hidden default
- The gap between "assigned" and "largest nearby" upstream area is a diagnostic — large ratios signal potential misassignment
- The preview map caption already displays this ratio ("Assigned: 588 km² · Largest nearby: 381,370 km²") — good; it should eventually carry an interpretive note when the ratio exceeds a threshold

### scenario 01 · Timbuktu — the desert intellectual capital *(works with current EDOPS)*

**User**: user01 — historian / Africanist with interest in medieval Islamic civilization and trans-Saharan trade

**Entry question**: *"Timbuktu was clearly a successful center of trade and Islamic scholarship during the Mali and Songhai empires. Given its location at the edge of the Sahara, how could that setting possibly support a civilizational center?"*

**Walkthrough**:

1. User types "Timbuktu" in the place lookup. WHG returns candidates including Tombouctou [ML] — exact match with alt name "Timbuktu". User selects it.
2. User checks bands A, B, C, E (physical + coastality) and F (temporal), enters `1350` to `1600` CE (Mali/Songhai peak).
3. Clicks "Get signature" → payload loads.

**What the signature shows**:

- **Band A (Physiographic)**: low flat plain at the Saharan margin, very low relief — confirms the surface reading of an inhospitable desert-edge location
- **Band B — local `s` values**: low precipitation, high aridity index, minimal local runoff — the site looks fragile
- **Band B — upstream `u` values**: the Niger headwaters drain the Fouta Djallon highlands in Guinea, where annual rainfall exceeds 1,500mm. The `s/u` divergence on precipitation is large — Timbuktu sits on a river fed by distant highlands, not its local catchment
- **Band C (Bioclimatic)**: local biome is Sahel/desert edge; upstream biome profile includes Guinea highland forest/savanna — the divergence is visible in vegetation productivity measures too
- **Band E (Coastality)**: not coastal in the marine sense, but `dist_sink` captures proximity to the river mouth system; the Niger Inland Delta immediately upstream creates an enormous productive floodplain — this is the ecological anchor
- **Band T (Temporal, 1350–1600)**: LMR PDSI for the period shows conditions broadly comparable to the modern mean in the Sahel; no catastrophic drought forcing during the empire peak; eVolv2k shows some volcanic events but no sustained forcing

**Payoff**: The signature resolves the paradox via allochthonous water. The Niger brings rainfall from Guinea highlands 1,500 km upstream, sustaining agriculture and the Niger Inland Delta fisheries that fed the city. The `s/u` divergence is the structural explanation. Timbuktu's genius loci is not its local environment but its position as the hinge between river-borne surplus (south) and trans-Saharan caravan trade (north) — the signature provides the physical half of that argument; the cultural-geographic half belongs to CDOP.

**Note**: this scenario is contingent on the neighborhood assignment problem (scenario 00) being resolved. If the default Level 08 containment basin is used, the signature understates the Niger's role.

**Design implications**:
- `s/u` divergence should be the lead display item in Band B, not buried
- Upstream biome contrast in Band C deserves a natural-language gloss ("your upstream basin spans X biomes")
- Band E needs prose interpretation — `dist_sink` values are not self-explanatory to humanities readers
- The narrative button should frame the interpretation around the user's question, not just describe values

### scenario 02 · Ur — the hyper-arid cradle *(exercises current limits)*

**User**: user01 — archaeologist / ancient Near East historian

**Entry question**: *"Ur is described as situated in a near-hyper-arid environment, yet it was among the earliest and most densely settled urban centers in the ancient world. How do I square that?"*

**Walkthrough**:

1. User types "Ur" in the place lookup. WHG returns no match. → **Fail state 1**: sandbox offers: enter lat/lon directly | search Geonames | LLM-assisted lookup. User enters coordinates (~30.96°N, 46.10°E) and proceeds.
2. User checks bands A, B, C, E and F (temporal), enters `−2100` to `−1800` (Ur III period).
3. Clicks "Get signature" → bands A–E load; Band T triggers **Fail state 2**: date range is prior to LMR coverage (floor ~0 CE). Sandbox notifies the user: "Temporal climate data is not available before approximately 0 CE. Ur III period climate is outside current EDOPS scope. Proceeding with physical signature only." Bands A–E render normally.

**What the signature shows (A–E)**:

- **Band A**: flat alluvial plain, very low elevation — expected
- **Band B — local `s`**: low precipitation, high aridity — confirms the paradox
- **Band B — upstream `u`**: Euphrates headwaters drain the Taurus and Zagros; `s/u` divergence on precipitation is large — allochthonous water again
- **Band C**: local desert/xeric biome vs. upstream alpine/temperate montane — strong contrast
- **Band E**: `dist_sink` near zero — Ur was at the head of the Persian Gulf in the third millennium BCE; high coastality index

**What the temporal question surfaces**: The user's climate question for the Ur III period is currently unanswerable within EDOPS. This is not merely a tool gap — pre-Common Era paleoclimate data at sub-basin resolution is a genuine research frontier. The fail state should say so honestly and note what *is* available (pollen cores, isotope records) as pointers for further research outside the tool.

**Design implications from fail states**:
- WHG no-match message must not be a dead end — offer lat/lon entry prominently as the primary fallback
- Temporal out-of-range notification should be informative, not just an error — name the data gap, suggest what bands still apply
- "Good luck" tone is appropriate: EDOPS is honest about what it can and can't do

### scenario 03 · Federico — enriching ancient place references via API *(API-driven; exercises temporal and spatial limits)*

**User**: user02 (Federico) — computational classicist / Graph-RAG researcher

**Entry need**: *"I am building a Neo4j knowledge graph over ancient texts about water infrastructure. Each place node should carry structured environmental context from EDOPS alongside its textual attestations. My places are in river-valley settings, and my time periods are pre-Common Era."*

**This scenario does not run through the sandbox GUI.** Federico calls the EDOP API directly and pipes the JSON signature into his graph ingestion pipeline. The sandbox may help him configure the right call — band selection, neighborhood type, level — but his working interface is the API.

**The two design questions Federico raised directly**:

1. **Chronological gap**: His corpus is pre-Common Era (e.g. Roman hydraulic engineering, Mesopotamian irrigation). Band T (LMR) has a floor of ~0 CE. For his core use cases, temporal enrichment is unavailable within current EDOPS scope. This is the same fail state as scenario 02, but it is not a rare edge case for Federico — it is his entire domain. *Implication*: the API response for out-of-range temporal queries must clearly document what is and is not available, and the signature JSON should be complete and useful for bands A–E even when F is absent.

2. **Spatial unit for river-valley settings**: Canals, aqueducts, and irrigation systems are engineered water — they cross basin boundaries by design. Point containment at Level 08 will regularly assign these sites to the wrong hydrological context. Federico's use case puts maximum pressure on the neighborhood selection problem. *Implication*: the API must expose neighborhood type as an explicit parameter (`basin`, `buffer`, `upstream`, `threeTier`), not hide it as a default. For his use, `upstream` or `threeTier` is likely the appropriate choice; `basin` (current default) may be systematically misleading.

**What a well-configured API call would look like for Federico**:
```
GET /api/signature?lat=30.96&lon=46.10&level=08&neighborhood=upstream&bands=A,B,C,E
```
Bands A–E, upstream neighborhood, no Band T (outside temporal coverage). Response: self-describing JSON ready for Neo4j node enrichment.

**API lens concept**: Federico's use case suggests a named lens — e.g. `lens=ancient_riverine` — that pre-configures neighborhood=upstream, bands=A–E, temporal=none, with appropriate caveats in the response metadata. Other researchers with similar profiles would benefit from the same defaults without having to reconstruct them.

**Design implications**:
- API must expose neighborhood type as an explicit, documented parameter
- Signature JSON metadata should include a `coverage` field noting which bands were returned and why any were omitted
- The temporal gap should appear in the response as structured metadata, not just a UI message
- API lens profiles are worth designing once two or three use-case clusters are well-characterized
