The competency questions are mine, and they should reflect my model commitments, not external use cases. 

What makes a good set of EDOPS competency questions, then. Some criteria:

They should be **answerable by the signature alone**, not by the signature plus external data. If the question requires Tracks of Yu events or D-PLACE attributes to answer, it's an application-level question, not a model competency question. The model is being tested on whether it produces the right kind of structured output, not whether downstream analyses succeed.

They should **cover the model's distinctive features**. The s/u duality, the coastality fields, the temporal scoping, the polygon aggregation, the band structure, the neighborhood parameterization — each is a design choice that makes EDOPS distinct from geographic enrichment or simpler basin-attribute lookup. The competency question set should exercise each of these features, because if the model can't answer the questions that demonstrate why those features exist, the features aren't justified.

They should be **operationally specific** — phrased so it's clear what input you provide and what output the model returns, not abstract framings of research interest. "Can the signature describe how a place's local hydrological setting differs from its upstream catchment?" is specific. "Can the signature address the urban hearth question?" is not.

They should be **testable** — you should be able to run them against the current implementation and see whether the answer is yes, partially, or no. Some will be answerable in v0.3, some will require Band F or coastality completion, some will require the federated-data architecture from Section 10. That's fine; the set defines the trajectory, not just the current state.

A first-cut list, organized around what the model uniquely claims to do:

**CQ-1.** Given a point and a basin level, return the local environmental signature — values for all selected variables aggregated over the containing basin polygon, with neighborhood metadata stating the aggregation extent.
*Tests: basic point-to-signature pipeline; variable population; metadata transparency.*

**CQ-2.** Given a point, return both the local (s) and upstream (u) values for variables where both are defined, alongside a divergence indicator.
*Tests: the s/u duality as a first-class architectural feature; whether the model exposes positional structure, not just description.*

**CQ-3.** Given a point on a marine-connected drainage, return its coastality fields — outlet type, flow distance to outlet, network depth from coast.
*Tests: whether the model treats coastality as a structurally distinct dimension from terrestrial signature, not as an outlier correction.*

**CQ-4.** Given a point and a historical period, return temporally scoped climate values appropriate to that period (LMR-derived for 1–2000 CE), distinguished from time-stable baseline variables (Bands A/B), and note where the period falls outside available temporal coverage.
*Tests: temporal scoping; band structure; honest reporting of what is and isn't temporally resolvable.*

**CQ-5.** Given a polygon, return signature distributions over intersecting basins — central tendency plus quantile distribution per variable — with metadata on the number and area of intersecting basins and on whether the polygon corresponds to a natural watershed.
*Tests: polygon input; distributional output rather than scalar summary; the lossy-aggregation honesty principle.*

**CQ-6.** Given a sequence of polygons with associated dates, return per-period signatures and a difference summary across the sequence.
*Tests: temporal-polygon support; the territorial-trajectory case worked through with Northern Song.*

**CQ-7.** Given a point, return the ecoregion membership and a typicality score relative to that ecoregion's signature distribution.
*Tests: ecoregion-as-reference-frame; outlier detection at the ecoregion scale.*

**CQ-8.** Given a point, indicate which variables are reliably populated and which are null, sentinel, or low-confidence at this location.
*Tests: data-quality transparency; the model's honesty about its own coverage.*

**CQ-9.** Given two points, return their signatures in a form suitable for comparison (same variable subset, same neighborhood model, same time scoping).
*Tests: comparison input/output stability; whether the signature format actually supports the pairwise operations downstream applications will perform on it.*

**CQ-10.** Given a point in a region covered by contributed regional data (per Section 10), return a signature that prefers contributed data where available and falls back to global baselines elsewhere, with per-field provenance.
*Tests: federated data architecture; provenance layer. (Future, not v0.3.)*

That's ten, which is too many for a public-facing rubric and probably about right for an internal design contract. They cluster naturally: CQ-1, CQ-2, CQ-3 are the core signature competencies; CQ-4, CQ-6 are temporal; CQ-5 is polygon; CQ-7 is ecoregion-relational; CQ-8 is metadata-honesty; CQ-9 is comparison-readiness; CQ-10 is the federated future.

For a public cookbook, you'd probably collapse these into something like five to seven public-facing competencies framed as "EDOPS can answer..." — and use the internal ten (or however many you settle on) as your design contract. The public list is for users; the internal list is for you.
